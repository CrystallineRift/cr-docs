# Capture Missions (Bond Trial, Phase 3)

A second battle-mission pool, layered onto the same server-tracked mission design
[Talents](25-talents.md)'s ability missions already use ([Battle Persistence](09-battle-persistence.md),
[Battle Extensions](?page=unity/24-battle-extensions)). Completing a capture mission arms a
**guaranteed capture** for the player's next Capture Crystal throw, rather than unlocking an ability.
Spec: `cr-api-unity/docs/superpowers/specs/2026-09-27-capture-missions-phase3-design.md`.

## The pool

`battle_mission_template.reward_type` decides which pool a row belongs to — `AbilityUnlock` rows are
the ability pool, `GuaranteedCapture` rows are the capture pool. No separate `category` column: the
reward type is already the fact that matters, and a second column would just have to agree with it.

Two mission types exist only for this pool (added to `CR.Game.Model.Battle.BattleMissionTypes`,
alongside the pre-existing `StatusApplication` / `KnockOut` / `ElementalReaction`):

| Type | What it counts | `threshold` means |
|------|-----------------|--------------------|
| `HitsWithoutSwitch` | A player `Ability` action that did not miss and dealt damage > 0. Any *applied* switch (voluntary or a forced faint-swap) resets the count to 0 and reports the reset; misses, items and rejected switches do not reset it. | An event count, same as the other types |
| `BelowHpWithoutKo` | A state check evaluated on **every** player action (including a failed capture throw's `Item` action): the target is alive and `TargetFinalHp × 100 ≤ threshold × TargetMaxHp`. Progress reports as 0/1. | An **HP percentage** (1-99), not an event count — the Studio editor labels the field "HP %" for this type |

`BattleMissionTypes.AllowedInCapturePool(type)` is every type except `KnockOut` — a fainted wild
creature can't be thrown at, so a KO-based capture mission would never complete on the creature the
throw needs to hit.

The nine starter capture missions (content_key `capture_trial_*`) ship in their own
`M20002SeedCaptureTrialMissions` (Game domain, block 20001-20099) — moved there in a Phase E cleanup
from a hand-merge into `M12005SeedBattleMissions_20260903`, which is an `<auto-generated>` Content
Studio export (`Do not hand-edit`); a hand-merge into it is silently lost the next time someone
re-exports the ability-mission pool. Both migrations guard on `content_key`, so a database that
already ran the old M12005 with the capture rows in it treats every M20002 insert as a no-op under the
same ids — no data moves, only which migration is allowed to own the rows going forward. See [Battle
Extensions](?page=unity/24-battle-extensions) for the authored table and
`Assets/CR/Content/Defs/BattleMissions/` for the Studio assets.

## Feasibility and the draw

A capture mission is only offered when the player's own team can actually complete it — a Bond Trial
that asks for Poison when nothing on the team can poison anything is not a hard trial, it's a broken
one that looks like a bug. `CR.Game.Compat.Battle.Missions`:

- **`CaptureMissionFeasibility`** is a pure closure over the player team's abilities and active
  reactions: it walks each candidate mission's condition against what the team's abilities can
  actually inflict (status conditions with `probability > 0`, or a reachable elemental reaction
  chain), and rejects the rest with a per-candidate reason (logged at info level, not an error — a
  talent simply having no trial this fight is normal, not broken).
- **`CaptureMissionDraw.Pick`** draws uniformly over the feasible set with
  `new Random(battleId.GetHashCode())` — deterministic per battle and reproducible from logs.
  Candidates are filtered *before* the draw, never after, so a bad filter is a bug in one pure
  function rather than a draw that silently favours whatever survived.

If nothing is feasible, the battle simply has no capture mission that fight.

## Lifecycle

1. **Assignment** — `BattleDomainService.AssignMissionsAsync` (called from `StartBattleAsync`) checks
   `TrainerModifiers.HasCaptureMission` (from `ITrainerModifierProvider`, owned by the Talents domain —
   the Bond Trial talent effect) and that the battle is wild (`Trainer2Id == BattleDomainService.WildTrainerId`,
   **not** the `battle_type` string — Unity starts wild battles as `"ONEvONE"`). When both hold, it
   builds team capabilities from `ICreatureInventoryService.GetTeamAsync`, runs feasibility, draws one
   mission, and folds it into the same `BattleMissionTracker` snapshot the ability mission already
   uses — one `battle.mission_state` column, one tracker, two pools.
2. **Tracking** — `ApplyMissionsAsync` re-persists the tracker's snapshot after every resolved action
   (the same seam that serves the ability pool), and sets `battle.guaranteed_capture_ready = true` the
   moment the capture mission's completion transition happens. The flag is **sticky**: it stays true
   on every later `ActionOutcome` until a capture actually clears it, so a HUD that missed the
   completion event still ends up showing the badge.
3. **The guaranteed throw** — `CaptureAttemptService.IsGuaranteedAsync` checks, on every capture
   attempt against a wild battle:
   - the battle is `Active`;
   - the thrower is `Trainer1`;
   - `Trainer2Id` is the wild sentinel;
   - the target is the wild's own active creature;
   - `battle.guaranteed_capture_ready` is set.

   When all five hold, `chance = 1.0f` — bypassing `CalculateChance` and its 5-95% clamp entirely,
   but still rolled through the same `_roll.Next() <= chance` comparison, so the roll seam itself is
   untouched by the guarantee.
4. **Clearing the flag** — `ClearGuaranteedCaptureAsync` runs only after a capture **commits**
   (including a storage-full capture — it still commits, so the flag and the crystal are both
   consumed together). A refused throw (wrong target, ended battle, wrong thrower) never touches the
   flag. A failure to clear it after a successful capture is logged and has no further effect: the
   creature is no longer wild, so a second guaranteed throw is refused as "not wild" regardless.

## Data

`battle.guaranteed_capture_ready` (`M20001AddGuaranteedCaptureReadyToBattle`, Game domain) is a
`BOOLEAN NOT NULL DEFAULT false` column — no JSON, no jsonb, ANSI on both engines. It is set to `true`
only by `UpdateMissionStateAsync`'s `markGuaranteedCaptureReady` parameter (which never sets it back to
`false`) and cleared only by `ClearGuaranteedCaptureAsync`. See
[Battle Persistence](09-battle-persistence.md) for the `battle` table and the mission-tracking seams
in full.

## Stat and quests

Every completion, in either pool, emits `BattleMissionCompleted` to `IProgressOutcomeSink`;
`LifetimeStatProjector` increments `battle_missions_completed` — see
[Stats and Lifetime Tracking](08-stats-system.md). Neither the tracker nor `BattleDomainService` ever
write the stat directly, and the player write routes already refuse a client-reported
`battle_missions_completed` (server-authoritative core rule).

## Authoring and deploy order

Content ships through the one standard pipeline: a `BattleMissionDefinition` SO pushed from
Crystalline Rift Studio to the live server, and the same SO exported back into
`M12005SeedBattleMissions_20260903` so the offline floor carries it too. The nine capture-pool rows
are the one exception — they live in their own `M20002SeedCaptureTrialMissions` (see "The pool"
above) rather than the generated export, so a future Studio re-export of the ability-mission pool
cannot silently drop them.
The Bond Trial **talent** that grants `TrainerModifiers.HasCaptureMission` is authored and exported
separately, through Talents' own `SeedTalentTrees_` file (block 15150-15199, not a 20xxx number) —
see [Talents](25-talents.md). Because the talent is useless without the pool it draws from, **the
capture missions must be pushed and deployed before the Bond Trial talent goes live**; an environment
that has the talent but not the missions simply finds no feasible candidate and logs it — not an
error, just an empty trial that fight.

## Rulings summary

- One tracker serves both pools; the reward type alone decides which pool a row is in (no `category`
  column).
- `guaranteed_capture_ready` is its own boolean column rather than a field inside the JSON snapshot,
  so the capture path never has to parse or rewrite the tracker's state to read or clear it.
- "Wild battle" is decided by the sentinel trainer id, never the `battle_type` string.
- Candidates are filtered before the draw; the draw itself is a uniform, deterministic pick.
- `BelowHpWithoutKo` reuses `threshold` as a percentage rather than adding a column — the editor and
  the validator both know the one type where it means something different.
- The legacy `CR.Game.Data.Constants.BattleMissionTypes` / `BattleMissionRewardTypes` copies were
  deleted once their only three consumers moved to `CR.Game.Model.Battle` (R7) and a grep confirmed no
  other reference remained.
